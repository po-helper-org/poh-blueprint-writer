# Груминг роем: карта уровня сеньор-архитектора

Первый проход автопилота даёт чистую по форме карту. Груминг делает её глубокой: каждую карточку,
задачу и этап разбирает отдельный агент с узкой ролью и своим чек-листом. Карточку смотрят
аудиторы с разных сторон, затем её переписывает агент, который видит все их находки сразу.

**Почему так.** Слабая модель теряет детали, когда держит в голове весь БФТ и всю карту. Узкий пакет —
одна цель, одна роль, вырезка из БФТ ровно под неё, чек-лист и строгий формат ответа — модель
отрабатывает на уровне сильной.

## Как запустить

Из папки проекта, после того как `./blueprint.py apply` даёт 0 ошибок:

```bash
./blueprint.py groom audit      # волна 1: пакеты аудита в groom/1-audit/
# … по агенту на каждый пакет → ответ в groom/1-audit/out/<имя пакета>
./blueprint.py groom refine     # волна 2: пакеты доработки с находками аудита в groom/2-refine/
# … по агенту на каждый пакет → ответ в groom/2-refine/out/<имя пакета>
./blueprint.py groom merge      # замены и вопросы — в план, затем apply и отчёт groom/report.md
```

**Рой.** Есть субагенты (Claude Code — инструмент Agent или Task) — запусти по агенту на каждый файл
`groom/<волна>/*.md`, пачками по 5–10 параллельно. Промпт агенту: «Выполни пакет `<путь>`. Ответ
запиши в `<волна>/out/<имя пакета>` строго в формате из пакета». Субагентов нет — выполни пакеты сам по очереди,
каждый с чистого листа: читай только пакет.

**Ведущий агент.** После `merge` прочитай `groom/report.md`:

- отклонённые замены — в нём причина; исправь план руками;
- находки «критично» без замены — исправь план;
- затем `./blueprint.py apply` до нуля ошибок, рубрика качества `autopilot.md` и `./blueprint.py build`.

Второй круг (`groom audit` → `refine` → `merge`) — когда в отчёте больше трёх критичных находок.

## Формат ответа пакета

```markdown
## Находки
- критично · BP-6.1 · Выход «счёт» никому не уходит: в ФТ-13 организатор получает письмо (ФТ-13)
- важно · BP-6 · В TOBE нет случая «денег хватает»
- мелочь · BP-6.1 · Название длиннее нужного

## Вопросы
| Кому | Вопрос | Где | Тип |
| --- | --- | --- | --- |
| PO | Каким каналом уходит счёт: письмо или кабинет? | BP-6.1 | вопрос |

## Замены
## BP-6.1 · Письмо организатору со счётом на пополнение
этап: D
слой: technology

<блок целиком, как в plan/map.md>
```

- **Находка** — строка `- <критично|важно|мелочь> · <ID задачи или карточки> · <что не так и как должно быть> (<ID требования>)`.
- **Вопрос** — только то, чего нет в БФТ; «Где» — ID задачи или карточки.
- **Замена** — только в волне доработки: блок целиком, с заголовком `## ID · Название`, ключами и всеми разделами. Новая карточка — блок с новым ID под своей задачей.
- Разделов без содержания не пиши. Не пиши ничего, кроме этих трёх разделов.

## Общие правила для всех ролей

1. Источник истины — БФТ в пакете. Нет в нём — `[УТОЧНИТЬ у {кого}]` и вопрос, не догадка.
2. Карта — высота БФТ: без API, таблиц, полей БД. Сервис после запуска, не работа над проектом.
3. Требования не теряй: ID из старого блока остаются в новом.
4. Пиши по-русски, коротко, для людей: задача до 80 знаков, карточка до 90.

## Линза: coverage

**Роль — аудитор покрытия.** Проверяешь, что каждое требование БФТ реализовано на карте по сути,
а не только упомянуто ID.

1. Для каждого ФТ, ИТ, НФТ найди задачу и карточку, где оно **сделано**: правило в «Управлении», шаг в «Процессе», экран.
2. ID есть в «Требованиях БФТ», но в карточках нет его сути — находка «критично».
3. Часть требования потеряна: условие, исключение, порог из текста ФТ — находка «важно».
4. Одно требование размазано по задачам без ясной границы — находка «важно»: чья часть какая.
5. БТ и ПТ: ценность из них есть в UserStory хотя бы одной карточки.

## Линза: fabrication

**Роль — охотник за выдумками.** Проверяешь, что на карте нет ничего, чего нет в БФТ.

1. Каждое число, срок, процент, канал (email, SMS, push), роль, система и команда — найди в БФТ.
2. Не нашёл — находка «критично» с цитатой и вопрос: кому задать, чтобы узнать.
3. Утверждение сильнее БФТ («всегда», «мгновенно», «автоматически» без источника) — находка «важно».
4. `[УТОЧНИТЬ]` из БФТ, который на карте стал фактом, — находка «критично».

## Линза: failures

**Роль — архитектор надёжности.** Проверяешь, что карта знает, что бывает, когда что-то идёт не так.

1. Каждая внешняя система и передача между системами: что, если она не ответила, ответила ошибкой, ответила дважды?
2. Каждое изменение состояния (оплачено, использовано, опубликовано): можно ли его потерять или повторить?
3. Права и доступ: кто может увидеть или изменить данные, нужна ли проверка роли.
4. Нефункциональное из БФТ (сроки, нагрузка, доступность): у какой карточки оно в «Управлении».
5. Сценарии «что если» из БФТ: у каждого есть ветка в «Процессе» или вопрос.

Ответ — на высоте БФТ: «если сервис проверки не отвечает — официант видит понятный отказ», а не
таймауты и ретраи. Нет ответа в БФТ — вопрос.

## Линза: teams

**Роль — архитектор границ.** Проверяешь, кто что делает.

1. Каждая задача — один результат одной команды; две команды в одной задаче — находка с предложением разделить.
2. Исполнитель задачи согласуется с «Зависимостями» БФТ; кандидаты — два и больше.
3. Механизм карточки называет того, кто исполняет; он согласуется с командой задачи или внешней системой.
4. Работа без владельца (ни одна команда не делает) — находка «критично» и вопрос.

## Линза: questions

**Роль — куратор вопросов.** Проверяешь таблицу «Вопросы».

1. Каждый `[УТОЧНИТЬ у X]` на карте — строка с «Кому» X и «Где» — ID, где он стоит.
2. Повторы — находка: какой оставить.
3. Блокер — без ответа задача не стартует; остальное — вопрос.
4. Вопрос сформулирован так, чтобы ответить одной фразой: «Каким каналом…?», «Кто делает…?».
5. Адресат — роль или человек из БФТ; не «команда», не «все».

## Линза: flow

**Роль — архитектор потока одного этапа.** Смотришь на этап как на цепочку: что пользователь делает,
что ему показывают, что происходит за кадром, что поддерживает.

1. Пройди шаги истории этапа. У каждого шага с экраном есть карточка technology, у каждой technology — backstage, который отдаёт ей данные.
2. Каждая передача — выход одной карточки равен входу другой со ссылкой `(BP-x.y)`. Нет ссылки — находка.
3. Чего не хватает между карточками, чтобы поток работал, — находка «критично»: какая карточка нужна.
4. Две карточки делают одно и то же — находка: объединить.
5. Линия видимости: в technology нет того, чего пользователь не видит; в backstage нет экранов.

## Линза: task

**Роль — техлид задачи.** Переписываешь постановку задачи так, чтобы команда начала работу без вопросов.

1. Зачем — одна фраза ценности для бизнеса из БТ или ПТ.
2. ASIS — как сейчас, из БФТ; не сказано — `[УТОЧНИТЬ у PO]`.
3. GAP — чего именно не хватает, по пунктам.
4. TOBE — как будет; каждое утверждение TOBE сделано в одной из карточек задачи. Нет карточки — добавь блок новой карточки `BP-N.k`.
5. HowToDemo — 2–4 шага «делаю → вижу», основной путь и хотя бы одно исключение.
6. Критерии приемки — проверяемые, по одному на каждое обещание TOBE.
7. Учти все находки аудита по этой задаче. Неприменимую — оставь и объясни в «Находках».

Ответ: «Замены» — блок задачи целиком и блоки новых карточек.

## Линза: card

**Роль — архитектор карточки.** Переписываешь карточку так, чтобы по ней мог работать аналитик.

1. Суть — одно действие сервиса: кто → что делает → какой результат.
2. UserStory — роль, которая получает пользу (человек, не команда); ценность — из БТ или ПТ.
3. JobStory — 1–3 ситуации; одна из них — исключение или отказ из БФТ, если он есть.
4. Вход — каждое данное с источником: `(BP-x.y)` или внешняя система.
5. Управление — каждое правило с ID требования; пороги и сроки — только из БФТ; относящиеся НФТ.
6. Выход — что меняется (состояние, сообщение, документ) и кому уходит `(BP-x.y)`.
7. Механизм — кто исполняет: команда или система.
8. Процесс — начинается с триггера, кончается результатом; основной путь и ветка на каждый «что если» из БФТ; участники работают в сервисе; 4–10 шагов.
9. HowToDemo — основной сценарий и хотя бы одна ветка; проверяемо руками.
10. Учти все находки аудита по этой карточке. Неприменимую — оставь и объясни в «Находках».

Ответ: «Замены» — блок карточки целиком.
