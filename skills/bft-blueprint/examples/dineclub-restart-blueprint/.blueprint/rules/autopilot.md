# Автопилот: от БФТ до Service Blueprint за один заход

Маршрут для агента, который строит карту сам, без PO. Каждый шаг: что сделать, какой командой, когда шаг
готов. Работает на любой модели: решения сведены в таблицы, форма — в шаблоны, проверки — в скрипты.

**Результат.** История `<epic>-story.md` со страницей, проект Backlog.md `<epic>-blueprint/`, страница карты
`<epic>-map.html` и архив `<epic>-blueprint.zip`. Линтер без ошибок, рубрика качества пройдена.

**Пути.** Ниже `S` — папка скриптов навыка (`<skills_path>/bft-blueprint/scripts`), `D` — папка эпика
(`<docs_path>/<epic>`), `P` — проект `D/<epic>-blueprint`. Внутри проекта те же скрипты вызываются
через `./blueprint.py`.

## Семь правил

1. **Только БФТ.** Каждый факт карты — из БФТ. Нет в БФТ — `[УТОЧНИТЬ у {кого}]` в тексте и строка в «Вопросах». Не догадывайся о командах, числах, каналах, сроках.
2. **Ничего не теряй.** Каждое ФТ, ИТ, НФТ — в строке «Требования БФТ:» задачи (BL017). Список даёт шаг 1.
3. **Пиши для людей.** Названия — по-русски, без API, эндпоинтов, таблиц и полей. Задача — до 80 знаков, карточка — до 90.
4. **Роль — тот, кто пользуется.** UserStory — от лица гостя, сотрудника, PO. Не «Как команда …» (BL033).
5. **Форма — по шаблону.** Копируй шаблон и заполняй места `{{…}}`. Пустой шаблон линтер не пропустит (PL007).
6. **Скрипты — судья.** Готово то, что прошло `./blueprint.py next` без ошибок. Читай подсказку «как исправить» под ошибкой.
7. **Не останавливайся на вопросах.** PO недоступен — вопрос уходит в «Вопросы», работа идёт дальше.

## Шаг 1. Инвентарь БФТ

```bash
python3 $S/bft-reqs.py $D/<epic>.md --out $D/<epic>-reqs.md
```

Прочитай `<epic>-reqs.md` целиком. Это рабочий лист на весь заход:

| Раздел листа | Куда идёт |
|---|---|
| 1. Требования | ФТ, ИТ, НФТ → задачи «Что делаем»; БТ, ПТ → история и UserStory |
| 2. Акторы | персонажи истории (люди, которые что-то видят) |
| 3. How to demo, UJM | этапы истории, «было → стало», HowToDemo задач |
| 4. Сценарий приёмки | шаги истории и «Процесс» карточек; `alt` — развилка |
| 5. Зависимости | команды «Карты» |
| 6. Ограничения | «Управление» карточек |
| 7. [УТОЧНИТЬ] | «Вопросы» истории и карты |

*Готово, когда* лист прочитан и ты знаешь: сколько ФТ, ИТ, НФТ, кто персонажи, какие команды.

## Шаг 2. История через экраны

Шаблон — `templates/story.md`, образец — `examples/golden_story.md`, правила — `resources/story_line.md`.

| Решение | Как принять |
|---|---|
| Персонажи | 1–3 из «Акторов»: кто пользуется результатом. Персонаж — **один человек в одной роли**: не «Менеджер, поддержка и контент» (ST025), а «Менеджер подключения»; остальные роли — шагами или отдельным персонажем. Команда, внешняя система, поисковик — не персонажи |
| Этапы | 3–6 моментов пути по времени: «Узнаю», «Выбираю», «Пользуюсь». ID — A, B, C. Подготовка до старта — первым этапом |
| Шаги | на персонажа: «было», 2–7 шагов, «стало». Шаг — фраза от первого лица: «Купил билет — и сразу вижу скидку» |
| Экраны | 1–2 на шаг, только те, что есть в БФТ (ИТ, макеты, How to demo). Состав — словами из словаря `story_line.md`: заголовок, текст, кнопка, оффер, список. Контур — место глазами человека из словаря; внешний сервис вне словаря (поисковик, кабинет вебмастера) — как он называется у пользователя, предупреждение ST023 допустимо |
| Вопросы | всё `[УТОЧНИТЬ]` из листа, что касается пути персонажа: «Кому», «Вопрос», «Где» — ID шага или экрана |

`status: Черновик` — PO историю не видел. Прогони:

```bash
python3 $S/bft-story-lint.py $D/<epic>-story.md
python3 $S/bft-story-render.py $D/<epic>-story.md
```

*Готово, когда* `bft-story-lint.py` даёт 0 ошибок.

## Шаг 4. План карты

Вся карта — один файл `plan/map.md` и по файлу на экран `plan/screens/F3.md`. Шаблоны —
`.blueprint/templates/map.md` и `screen.md`, образец — `examples/dineclub-restart-plan/` навыка.

**Начни с каркаса** — так ничего из БФТ не потеряется:

```bash
./blueprint.py skeleton            # plan/map.md: задача на каждое ФТ, карточки правил, экранов и ролей;
                                   # «Управление», критерии приёмки, JobStory, вопросы — уже из БФТ
./blueprint.py groom fill          # пакет на каждый блок с {{…}} в groom/0-fill/
# … по агенту на пакет (или сам, пакет за пакетом) → ответ в groom/0-fill/out/<имя пакета>
./blueprint.py groom merge fill    # ответы — в план; отчёт groom/report.md: что осталось незаполненным
```

Каркас пишет только то, что есть в БФТ; остальное — места `{{подсказка}}`, а `apply` не примет план,
пока они есть (PL007). Готовое из каркаса не удаляй: строки «Управления», критерии приёмки, ID
параметров (`P7`) — их проверяют BL036–BL038. Раскладку можно менять: перенести карточку в другую
задачу, объединить две — ID требований и параметров переезжают вместе с текстом. Где лежит каждый
атом БФТ — `plan/skeleton.md`. Правила ниже — что должно получиться в каждом блоке.

Без каркаса пиши по порядку: команды → задачи этапа A с их карточками → этап B → … → экраны → вопросы.

### 4.1 Команды

Из «Зависимостей»: команда — тот, кто **делает и владеет** куском работы. ID — латиницей, коротко.

| В «Зависимостях» | Команда |
|---|---|
| команда, сервис, витрина, приложение со своим владельцем | своя строка: `vit · Витрина`, `teama · TeamA` |
| подрядчик, дизайн, маркетинг | своя строка, если делает работу на карте |
| внешняя система (поисковик, платёжка, CRM) | одна строка `ext · Внешние системы` |
| один человек «Разработка (Иван)» на всё | раздели по системам, которые он делает: «Direct», «Сайт» — две команды. Не знаешь — одна команда, вопрос в «Вопросы» |

### 4.2 Задачи «Что делаем»

Одна задача — один результат одной команды на одном этапе. Начинай с ФТ и ИТ, НФТ — в «Управление».

| Ситуация | Как резать |
|---|---|
| ИТ — экран или канал | задача команды, которая его делает: «Блок акции на странице после покупки» |
| ФТ — правило или процесс за кадром | задача команды-владельца: «Проверка билета: одна покупка — одна скидка» |
| одно ФТ на две команды | две задачи, у каждой своя часть, ФТ — в обеих строках «Требования БФТ:» |
| ФТ со сплошным [УТОЧНИТЬ] | задача `вид: уточнить`, вопрос — в «Вопросы» |
| НФТ — порог, срок, нагрузка | строка «Управление» карточки, которую ограничивает; своя задача — только если это отдельная работа |

Ключи: `этап:` — ID этапа истории, на котором результат виден; `вид:` — `создать`, `доработать`,
`используем` (готовое без доработки), `уточнить`; `команда:` — ID; не ясно — `кандидаты: a, b`, **два и
больше**. Один кандидат — это и есть исполнитель: `команда: a` и вопрос в «Вопросы» (BL035).

Описание задачи — по шаблону: зачем (одна фраза для бизнеса); `Требования БФТ: …`; ASIS — как сейчас;
GAP — чего не хватает; TOBE — как будет; HowToDemo — 2–4 шага «делаю → вижу»; критерии приемки —
2–4 проверяемых пункта.

### 4.3 Карточки «Как это работает»

У каждой задачи 1–3 карточки `BP-N.1`, `BP-N.2`. Карточка — то, что **происходит, когда сервис уже работает**, а не работа команды над ним.

| Не карточка | Почему | Куда |
|---|---|---|
| «PO утверждает состав полей», «СА сверяет параметры» | работа над проектом: PO, СА, разработка строят сервис, а не работают в нём (BL034) | задача «Что делаем» или вопрос |
| «Перечень отчётов для партнёров», «Документ состава полей» | документ или решение, а не то, что происходит | «Дополнительно» задачи или вопрос |
| «Механизмы платформы: тарифы, скидки, фильтры» | список механизмов | по карточке на то, что механизм делает для пользователя |

Задача `вид: уточнить` тоже получает карточку: как сервис **должен** работать, с `[УТОЧНИТЬ у …]` в неизвестном месте, а не процесс выяснения.

| Слой | Когда | Пример |
|---|---|---|
| `employee` | сотрудник на виду у пользователя что-то делает | «Официант даёт скидку и фотографирует чек» |
| `backstage` | сотрудник работает, но он не персонаж истории и его никто не видит | «Оператор сверяет чеки за день» |
| `technology` | то, что видит персонаж истории: экран, письмо, уведомление; админка — тоже, если персонаж — сотрудник, который в ней работает | «Страница после оплаты показывает блок акции», «Раздел «Вопрос-ответ» в карточке Direct» |
| `backstage` | наша система делает за кадром | «Проверка билета: активен, не использован, ≤7 дней» |
| `support` | общий ресурс или внешняя система, которая работает в момент сервиса | «Email и SMS; push — если канал есть», «1С принимает выгрузку», «Банк присылает выписку». Не документ, не решение, не перечень |

Порядок разделов карточки — шаблон:

- **Суть** — одна-две фразы.
- **UserStory** — «Как <кто пользуется>, я хочу <действие>, чтобы <ценность>». Для backstage-карточки роль — тот, кому служит результат: официант, гость, PO.
- **JobStory** — 1–3 ситуации «- Когда <ситуация>, хочу <действие>, чтобы <результат>». После «Когда» — строчная буква: «Когда нужно…», не «Когда Нужно…». После «хочу» сразу глагол: «хочу скрыть вопрос, чтобы…», а не «хочу, чтобы вопрос скрылся». То же в UserStory. Роль — человек: «бухгалтер», не «бухгалтерия».
- **Параметры** — четыре строки, значения через `;`:
  - Вход — что пришло, `(BP-x.y)` — от какой карточки;
  - Управление — правила с ID требований `(ФТ-1)`, НФТ, ограничения;
  - Выход — что отдаёт, `(BP-x.y)` — какой карточке;
  - Механизм — кто и чем исполняет.
- **Процесс** — 3–8 шагов `- Участник: действие`. Участник — человек или система, которые работают **в сервисе**: «Официант», «Приложение-сканер», «Каталог UnitB». PO, СА, разработка, «команда» — не участники (BL034). Развилка — `- ? Вопрос?`, под ней ветки `  - да → Участник: действие` и `  - нет → конец`. Ветки сходятся в следующий шаг.
- **HowToDemo** — 2–3 шага «делаю → вижу».

**Ссылка `(BP-x.y)` — только на карточку**, не на задачу `BP-x` (BL009).

Связи — главная ценность карты: выход одной карточки — вход другой. Пройди путь персонажа по этапам и
проверь, что каждая карточка получает вход от предыдущей или отдаёт выход следующей (BL028).

### 4.4 Экраны

На каждый экран из «Экраны» истории — `plan/screens/<ID>.md` по шаблону `screen.md`:

- `## Product` — 2–4 заметки «Когда …, хочу …, чтобы …» с `Источник: ИТ-1`;
- `## Design` — где и когда, главное на экране, куда дальше;
- `## Functions` — сценарии **Дано / Когда / Тогда**, alt-ветки — отдельными сценариями.

В задаче и карточке, которые делают экран, — строка `экраны: F3`.

### 4.5 Вопросы

Каждый `[УТОЧНИТЬ у X]` плана — строка таблицы «Вопросы»: ID `В1…`, «Кому» — X, «Где» — ID задачи или
карточки, «Тип» — `блокер`, если без ответа задача не стартует, иначе `вопрос`, «Ответ» — `—`.

### 4.6 ADR и Системные требования

Если на карте есть карточки слоя Technology — секции этапа в плане (структура таблиц —
`resources/backlog_rules.md` §этапа, шаблоны документов — `templates/adr.md`, `templates/sysreq.md`):

- `## Варианты` — не меньше двух, оценки по осям «Надёжность / Скорость реализации /
  Соответствие требованиям» и явное «Почему нет»; выбранному — «выбран»;
- `## Решение TO-BE` — по контракту на строку: ID выбранного варианта, суть и обоснование;
- `## Узкие места` — где TO-BE просядет: тип (нагрузка/надёжность/данные), оценка, риск,
  как прощупать до релиза;
- `## Компромиссы` — чем платим по оси «надёжность vs скорость реализации vs соответствие»;
- `## Контракты` — системные требования: по каждому контракту из TO-BE три вопроса —
  данные контракту, источник каждого параметра (система/поле/справочник), преобразования.

`apply` создаёт документы «ADR» и «Системные требования» и раскладывает эти секции; «Контекст»,
«AS-IS», «Диаграмма AS-IS/TO-BE» (mermaid) и «Открытые вопросы» допиши в документах сам
(`./backlog.py doc update`), вопросы продублируй в «Вопросы» «Карты» («Где» — ID контракта K1).
Нет карточек Technology — секций нет, документов нет (AR005 подскажет, если забыл).

## Шаг 5. Применить и довести до нуля

```bash
./blueprint.py apply
```

`apply` раскладывает план в бэклог и проверяет карту, сверяя её с БФТ рядом с папкой проекта (другой путь — `--source БФТ.md`). Ошибка показывает строку плана, код и подсказку.
Исправляй план и повторяй `apply`, пока ошибок нет. Порядок исправлений:

1. **PL** — форма плана: заголовки, ключи, шаблон;
2. **BL017** — потерянные требования;
3. остальные **BL** и **SN** — по подсказкам;
4. предупреждения — исправь все, которые можешь; оставшиеся назови в итоге.

Больше 8 кругов — остановись и опиши в итоге, что не сходится.

Частые ошибки первого круга — проверь план до `apply`:

- HowToDemo из одного шага — нужно 2 и больше, нумерованно (BL007, BL009);
- «я хочу, чтобы …» — после «хочу» сразу глагол (BL030);
- ссылка `(BP-3)` на задачу вместо карточки `(BP-3.1)` (BL009);
- задача без карточки (BL021), карточка без входа и выхода к другой карточке (BL028);
- требование из листа шага 1 не попало ни в одну строку «Требования БФТ:» (BL017);
- «Когда Нужно …» с заглавной (BL030), `кандидаты:` с одним ID (BL035), PO или СА в «Процессе» (BL034).

## Шаг 6. Рубрика качества

`./blueprint.py next` печатает блок «качество:» — числа карты. Строка с `!` — слабое место: исправь его
первым. Затем перечитай `plan/map.md` и ответь на каждый пункт. «Нет» — исправь план и повтори шаг 5.

| # | Проверка | Плохо → хорошо |
|---|---|---|
| 1 | На каждом этапе истории есть задача | этап «Письмо» пуст → задача «Один акцентный офер в письме с билетом» |
| 2 | Задача — результат, а не активность | «Работа над страницей» → «Блок акции на странице после покупки» |
| 3 | Команд больше одной, если систем больше одной | всё у «Разработки» → «Direct» и «Сайт» отдельно |
| 4 | Есть карточки technology и backstage | только backstage → экран, который видит пользователь, — technology |
| 5 | UserStory — от лица пользователя | «Как команда TeamA…» → «Как официант, я хочу сразу видеть ответ проверки…» |
| 6 | Процесс начинается с того, кто действует, и кончается результатом | «Система: обрабатывает» → «Официант: сканирует штрихкод … Приложение: показывает «Скидка 10%»» |
| 7 | В процессе два участника и больше, если есть передача | одна дорожка → «Сканер» передаёт, «TeamA» проверяет |
| 8 | Связи `(BP-x.y)` складываются в цепочку пути | карточки-острова → выход проверки — вход экрана результата |
| 9 | HowToDemo проверяем руками | «Проверить работу» → «Сканирую тот же билет снова — отказ «использован»» |
| 10 | Нет выдуманных чисел, каналов, сроков | «push за 2 часа» без ФТ → `[УТОЧНИТЬ у PO]` и вопрос |
| 11 | Каждое `[УТОЧНИТЬ]` — строка «Вопросов» | вопрос в тексте без строки → строка с «Кому» и «Где» |
| 12 | Названия читаются за секунду и без техники | «POST /check ticket_id» → «Проверка билета по штрихкоду» |
| 13 | Каждая карточка — про работу сервиса, не про работу над проектом | «СА сверяет состав полей» → «Карточка партнёра показывает, каких данных не хватает» |
| 14 | Персонаж — один человек | «Продажи, финансы и бухгалтерия» → «Бухгалтер» и, если нужно, «Менеджер по продажам» |
| 15 | Внутренние коды и сокращения раскрыты | «API v2», «движок правил», ключи задач трекера в названиях → слова пользователя; ключ трекера — в «ссылки:». ID из БФТ (ФТ-3, ПТ-А1, P7, I2) — не код: оставь ID и раскрой словами рядом — «P7 эксклюзив тарифа» (BL037) |

### 6.1 Груминг роем

Карта чистая по форме, но её надо углубить (большой БФТ, слабая модель, больше трёх `!` в рубрике) —
груминг по `.blueprint/rules/grooming.md`: `./blueprint.py groom audit` → агенты по пакетам →
`groom refine` → агенты → `groom merge`. Каждый пакет — одна цель и вырезка БФТ под неё.

## Шаг 7. Сборка и итог

```bash
./blueprint.py build
```

Итог одним сообщением:

- блокеры и открытые вопросы «кому — что»;
- предупреждения, которые остались, и почему;
- что PO стоит проверить первым: историю и спорные решения шага 4.

- Блок — заголовок `## <ID> · Название`, сразу под ним строки `ключ: значение`, пустая строка, описание.
- ID задачи — `BP-N` по порядку, карточки — `BP-N.M` под своей задачей.
- Ключи задачи: `этап`, `вид`, `команда` или `кандидаты`, по желанию `экраны`, `документы`, `ссылки`.
- Ключи карточки: `этап`, `слой`, по желанию `команда` (иначе — команда задачи), `экраны`, `ссылки`.
- `### BPMN` не пиши: схему соберёт `apply` из «Процесса».
- Правки после `apply` — в плане и снова `apply`. План потерян — `./blueprint.py export --force` вернёт его из бэклога.

Коды формы плана — `PL001`–`PL007` (`scripts/bft_plan.py`), карты — `BL`, экранов — `SN`
(`resources/backlog_rules.md`, `resources/screen_notes.md`).
