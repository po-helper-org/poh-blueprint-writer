# Контракты стыков — Design First

Карта говорит, **что** происходит на шаге пути. Контракт говорит, **как стыкуются системы**, чтобы
шаг прошёл: кто кого вызывает, какие поля уходят и приходят, откуда каждое поле в БФТ, что
возвращается при отказе, через какую цепочку данные превращаются в ответ, какие данные нужны из
хранилища. Контракты читают фронт, бэк и внешняя сторона, по ним же соберётся прототип.

Один контракт — один файл `contracts/C-N.md` в папке проекта, по шаблону `.blueprint/templates/contract.md`.
Проверка — `./blueprint.py contracts`: коды CT, 0 ошибок до показа.

## Команда согласования контрактов

Отдельный этап — **согласование технических контрактов** между фронтендом и бэкендом, сервисами и базой данных.
Его задача — снять неопределённость у бэкенда: что именно реализовать на стыке и зачем.

- **Когда.** Только там, где взаимодействуют два сервиса: карточки «Как это работает» разных систем связаны
  стрелкой и между ними идёт обмен данными (API) или запись и чтение из хранилища (база данных). Связь без
  обмена данными — строка `contracts/not-seams.md`.
- **Вход.** История «Что делаем» со стыком, требования БФТ из её строки «Требования БФТ», «Процесс» и «Параметры»
  карточек этой истории (`cards:` контракта).
- **Выход.**
  - контракт `contracts/C-N.md`: операция, поля запроса и ответа, пример, ошибки, взаимодействия (Sequence),
    цепочка за кадром, для базы данных — какие данные нужны;
  - **Swagger** `contracts/openapi.yaml` (OpenAPI 3) — `./blueprint.py contracts openapi`, пересобирается и при
    `./blueprint.py build`. По нему поднимается mock-сервер: `npx @stoplight/prism-cli mock contracts/openapi.yaml`,
    или MockAPI прототипа.
- **У каждого поля** — тип, обязательность (`Обяз.`: да или нет — и в запросе, и в ответе), источник в БФТ и
  **«Зачем потребителю»**: что поле даёт тому, кто его получает («показать официанту причину отказа»). Без
  назначения — `CT023`.
- **Уровни.** API — `boundary: frontend-backend`, `service-service`, `external` с `op: МЕТОД /путь`; база
  данных — `boundary: service-db` с разделом «Данные».

На карте — вкладка **«Контракты»**: список технических контрактов по типам стыка (Frontend → Backend,
сервис → сервис, внешняя система, база данных). Клик открывает контракт: операция, взаимодействия, поля с
обязательностью и назначением, пример, ошибки, цепочка, ссылка на Swagger.

## Контракт и документ «Стыки»

Этап «Контроль стыковочных работ» собирает документ «Стыки»: кто кому что предоставляет, к какому сроку,
контрольные точки и риски (S1…, D1…, K1…). Контракт `C-N` — **что именно** уходит по стыку: поля, ошибки,
Sequence, цепочка. Связь — в таблице «Контракты стыков» документа «Стыки»: в «Требовании к фиксации»
ссылайся на контракт (`C-3: эндпоинт, поля, ошибки — contracts/C-3.md`), а не переписывай поля второй раз.

## Контракт — проектное решение

БФТ говорит, **что** должно произойти и какие данные для этого нужны. Метод, путь, имена полей,
коды ошибок и пример ответа в БФТ не пишут — их **проектирует контракт**, и это не выдумка, а работа
Design First. Выдумкой было бы новое требование: поле, которое не нужно ни одному требованию, порог
или правило без источника. Поэтому:

- метод, путь, имя поля, код ошибки — называешь сам, по смыслу требования и «Процесса» карточек;
- у каждого поля «Источник» — требование, которому это поле нужно (ФТ, ИТ, ПТ, параметр P5, инвариант I2), а не место, где поле «написано»;
- значение, которого нет в БФТ (лимит, срок, канал), — `[УТОЧНИТЬ у …]` в «Источнике» и строка «Вопросов» карты; в примере ответа — правдоподобное значение того же типа.

## Когда нужен контракт

Решение по таблице, без обдумывания:

| На карте | Контракт |
|---|---|
| связь `(BP-x.y)` экрана Technology с карточкой Backstage — даже у одной команды | **да**, обычно `frontend-backend` — обе карточки в `cards:` (иначе `CT020`) |
| связь `(BP-x.y)` между карточками разных команд, одна из них в Backstage | **да**, `service-service` |
| внешняя система вызывает нас или мы её (партнёр, сканер, провайдер билетов) | **да**, `boundary: external` |
| экран Technology получает или отправляет данные | **да**, `boundary: frontend-backend` |
| карточка Backstage читает или пишет своё хранилище | **да**, `boundary: service-db` |
| связь с карточкой Support (поддержка в нештатной ситуации) нашей команды | нет — это работа людей, не обмен данными систем |
| связь двух карточек Backstage одной команды | нет — это одна система изнутри |
| стык по правилам выше, но по нему не ходят данные между системами (ручная передача, решение человека) | нет — строка в `contracts/not-seams.md` с причиной; `CT020` по нему молчит |

Файл `contracts/not-seams.md` — одна таблица:

```markdown
| Откуда | Куда | Почему не обмен данными |
| --- | --- | --- |
| BP-4.1 | BP-2.3 | правило редактирования — договорённость команды, данные между системами не передаются |
```

Причина проверяется (`CT013`): только стыки с карты, фразой. Данные ходят — нужен контракт, а не строка.

## Шапка

| Поле | Что писать |
|---|---|
| `id` | `C-1`, `C-2` … — совпадает с именем файла; номера не перенумеровываются |
| `title` | что происходит на стыке фразой для человека: «Официант сканирует билет» |
| `boundary` | `external` · `frontend-backend` · `service-service` · `service-db` — по таблице выше |
| `caller`, `callee` | кто вызывает и кто отвечает: команда из «Команд» карты или система из «Процесса» карточки |
| `op` | `МЕТОД /путь`: GET — прочитать, POST — создать или выполнить действие, PATCH — изменить часть, DELETE — убрать. Путь — `/v1/<сущность во мн. числе>[/{id}][/<действие>]`. У `service-db` строки нет |
| `cards` | ID карточек «Как это работает», которые обслуживает стык |

## Разделы

| Раздел | Обязателен | Как заполнять |
|---|---|---|
| `## Запрос` | кроме `service-db` | `| Поле | Тип | Обяз. | Где | Источник | Зачем потребителю |`: поле латиницей `snake_case`; тип `string · integer · number · boolean · array · object`; `Обяз.` — да/нет; `Где` — `path · query · body · header`; параметр пути `{id}` — строкой с `path` (`CT010`); «Зачем потребителю» — что поле даёт вызываемой стороне (`CT023`) |
| `## Ответ` | кроме `service-db` | `| Поле | Тип | Обяз. | Источник | Зачем потребителю |`: хотя бы одно поле; вложенное — через точку: `promo.discount`, элемент списка — `items.name`; «Зачем потребителю» — что поле даёт вызывающей стороне (`CT023`) |
| `## Пример ответа` | кроме `service-db` | блок ```` ```json ```` с каждым полем «Ответа» — из него MockAPI прототипа отдаёт ответ. Значения — как их вернёт система, с типом из «Ответа»: `10`, `"valid"`, `true`, `"2026-03-01"`; пояснение и ID требования вместо значения — `CT012` |
| `## Ошибки` | у `external` | статус 4xx/5xx, код латиницей `ЗАГЛАВНЫМИ_С_ПОДЧЁРКИВАНИЕМ` (`TICKET_NOT_FOUND`, не по-русски), когда — по-русски со ссылкой на требование. У внутренних стыков без ошибок — `CT022` |
| `## Sequence` | кроме `service-db` | `- Кто -> Кому: вызов(поля)` и `- Кто --> Кому: поля ответа`. Первая строка — `caller -> callee`, на каждый вызов — ответ |
| `## Цепочка` | когда в Sequence больше двух участников (`CT021`) | шаг · кто · вход · что делает · выход. Вход — поля «Запроса» или выходы прошлых шагов, ответ собирается из выходов (`CT008`). Группа полей — `ticket{status, event_date}` |
| `## Данные` | у `service-db` | хранилище и **какие данные нужны** обычными словами — без таблиц, ключей, индексов и SQL (`CT009`): устройство хранилища — работа СА |

## Источник каждого поля

У каждого поля запроса, ответа и строки данных — `Источник`: ID требования из БФТ (`ФТ-4`, `ИТ-3`,
`ПТ-1`) или `[УТОЧНИТЬ у {кого}]` (`CT005`). Поле без требования — выдумка: либо убери, либо
вопрос в «Вопросы» карты. ID копируй из `./blueprint.py reqs`; с БФТ рядом линтер сверяет их (`CT006`).

## Направление и ключи цепочки

**Кто вызывает.** `frontend-backend` — экран вызывает сервис: в `cards:` есть карточка экрана (technology или
employee), `caller` — сторона этого экрана. Сервер сам шлёт данные экрану (счёт выставлен, статус записи
изменился) — это `service-service`, а экран узнает о нём на шаге, где показывает результат (`CT014`).

**Откуда ключ.** Каждый обязательный ключ запроса — `id`, `*_id`, `*_ref`, параметр пути — кто-то выдал:

| Откуда ключ | Как записать |
|---|---|
| его создаёт другой стык (оплата → `payment_id`, запись → `booking_ref`) | поле с тем же именем в «Ответе» того стыка; список отдаёт `items.id` — тоже годится для `item_id`, если путь или поле списка называются по сущности (`GET /v1/service-centers` → `center_id`) |
| он приходит из внешнего мира: билет, письмо, профиль клиента, учётная система партнёра | «Источник» — требование и слово **«извне»**: `ФТ-1, извне: штрихкод с билета` |

Ключ, которого не отдаёт ни один ответ и который не помечен «извне», — разрыв цепочки (`CT015`): прототип не
сможет пройти шаги по порядку, а разработка не узнает, где ключ берётся.

## Фронт и бэк видят разное

- **Фронту** хватает шапки, «Запроса», «Ответа», «Ошибок» и примера: что отправить и что показать.
- **Бэку** — ещё «Sequence» и «Цепочка»: к кому он обращается дальше и как вход превращается в ответ.
- **Хранилищу** — отдельный контракт `service-db`: какие данные нужны и по какому требованию.

Сложная обработка за кадром не расписывается во фронтовом контракте: фронт видит вход и выход,
а цепочку — тот же контракт в разделе «Цепочка».

## Проверка

| Код | Что ловит |
|---|---|
| CT001 | файл не контракт: frontmatter, `id` = имя файла, повтор ID |
| CT002 | шапка: поля, `boundary` из списка, `op` «МЕТОД /путь» |
| CT003 | `cards:` ссылается на карточку, которой нет |
| CT004 | разделы и колонки шаблона, имена полей, пример ответа с полями ответа, ошибки внешнего стыка |
| CT005 | у поля нет источника |
| CT006 | ID требования нет в БФТ |
| CT007 | Sequence: начало с `caller -> callee`, ответ на каждый вызов, участники известны карте |
| CT008 | цепочка: вход без источника, поле ответа не собрано |
| CT009 | устройство хранилища в «Данных» или «Цепочке» |
| CT010 | параметр пути не описан в «Запросе» |
| CT011 | в контракте остались места `{{…}}` каркаса |
| CT012 | пример ответа: значение не того типа или пояснение вместо значения |
| CT013 | `not-seams.md`: строка не про стык карты или без причины |
| CT014 | направление: `frontend-backend` без экрана в `cards:` или экран на стороне `callee` — сервер шлёт экрану сам |
| CT015 | ключ цепочки (`id`, `*_id`, `*_ref`, параметр пути) не отдаёт ни один «Ответ» и он не помечен «извне» |
| CT020 | предупреждение: стык на карте без контракта и без строки в `not-seams.md` |
| CT021 | предупреждение: за вызываемой системой есть участники, а «Цепочки» нет |
| CT022 | предупреждение: внутренний стык без единой ошибки |
| CT023 | предупреждение: у поля запроса или ответа не сказано, зачем оно потребителю |
