# Прототип по контрактам

Команда «Прототип» — `/bft-blueprint <epic> --prototype`. Из готовой карты и контрактов собирается
показ для заказчика: история через экраны, которую проходят шаг за шагом. Клиентское приложение,
приложение сотрудника, админка и внешняя сторона — в одной странице; на каждом шаге со стыком справа
видно, **как это работает**: Sequence, метод, поля запроса и ответа с источником в БФТ, ошибки,
цепочка за кадром и какие данные нужны из хранилища. MockAPI (FastAPI одним файлом) отвечает по
контрактам: пример ответа, ошибки по выбору, 422 без обязательного поля.

**Решения не нужны.** Экраны — из «Истории» как есть (закрытый словарь элементов), данные — из
контрактов, раскладку шагов и вызовов делает каркас. Модель вписывает только **значения для демо**
и проверяет раскладку. Ничего не рисуется и не придумывается: нет экрана в истории — нет экрана в
прототипе; нет поля в контракте — нет поля на экране.

## Маршрут

Перед стартом: карта собрана (`./blueprint.py next` — «готово»), контракты без ошибок (`./blueprint.py contracts`).

```bash
./blueprint.py prototype skeleton   # prototype/spec.md: шаги истории по этапам, вызовы, экраны успеха и отказа
# заполни места в двойных фигурных скобках — значения для демо
./blueprint.py prototype lint       # коды PT до нуля (и CT — контракты)
./blueprint.py prototype build      # prototype/: web, api, docker-compose.yml
```

Показ: `cd prototype && docker compose up` → http://localhost:8080 (MockAPI — http://localhost:8000/docs).
Без Docker — открыть `prototype/web/index.html`: те же ответы считаются в браузере.

Замечания заказчика: кнопка «Замечания» → клик по точке экрана → текст; «Выгрузить» → `review.json`.
`./blueprint.py prototype review review.json` → строки «Вопросов» плана карты, «Где» — карточка шага;
затем `./blueprint.py apply` — красные точки на карте.

## План показа `prototype/spec.md`

Шаблон — `.blueprint/templates/prototype.md`. Шаг — блок:

```markdown
## Ш13 · Гость показывает билет — сканируем
приложение: staff
экраны: F2
вызов: C-3
ввод: barcode = 4600123456789; restaurant_id = r-12
показать: status, discount, reason
успех: F3
отказ: F4 = TICKET_NOT_FOUND
заметка: официант видит ответ сразу — без звонка в поддержку
```

| Ключ | Что | Кто решает |
|---|---|---|
| `## Ш13 · …` | шаг «Истории»; `## C-3 · …` — внешняя сторона вызывает наш сервис без экрана | каркас |
| `приложение` | `client` — клиент; `staff` — сотрудник рядом с клиентом; `admin` — админка, кабинет; `external` — внешняя система | каркас: по персонажу и контуру экрана |
| `экраны` | экраны «Истории» до вызова; `—` — вызов за кадром, экран — уже результат | каркас |
| `вызов` | контракты, которые запускает кнопка или камера экрана; несколько — через запятую; `—` — без вызова | каркас (таблица ниже); место `{{…}}` — выбери из подсказки |
| `ввод` | обязательные поля «Запроса» — `поле = значение` через `;` | **модель**: правдоподобное значение того же типа |
| `показать` | поля «Ответа», которые человек видит после вызова | каркас: все поля ответа; убери лишние |
| `успех` | экран после успешного ответа | каркас |
| `отказ` | `экран = КОД` — экран альтернативного вида и код из «Ошибок»; экрана нет — `— = КОД` | каркас |
| `заметка` | что важно сказать заказчику на шаге, одной фразой | модель, по желанию |

### Как каркас раскладывает вызовы

| Ситуация | Решение |
|---|---|
| карточка контракта показывает экран шага | шаг — кандидат на вызов |
| `GET` (прочитать) | на каждом кандидате: экран сам загружает данные, `успех` — тот же экран |
| остальное | один запускающий шаг: контур экрана = `caller` (+3), камера (+2), кнопка (+1), приложение сотрудника (+1) |
| у запускающего экрана нет кнопки и камеры | вызов за кадром: `экраны: —`, `успех` — экран результата (оповещение, «Подключён») |
| экран альтернативного вида рядом | `отказ: F4 = КОД`, код — первый из «Ошибок» |
| внешний контракт, который не вызывается ни с одного экрана | свой шаг `## C-N · …` с `приложение: external` |

### Значения для демо

- **Тип — из «Запроса»**: `integer` — число без кавычек (`10`), `boolean` — `true`/`false`, `string` — текст.
- **Правдоподобно и по БФТ**: число или срок из БФТ — то же значение (скидка `10`, окно `7`); ID — короткий
  читаемый код (`r-12`, `g-1024`); дата — `2026-11-14`; штрихкод — 13 цифр.
- **Одно значение — на весь показ**: тот же `restaurant_id` на всех шагах, где он есть.
- Значение, которого нет в БФТ и не придумать без решения бизнеса, — всё равно правдоподобное: показ — не
  требование; вопрос о нём уже живёт в «Вопросах» карты.

## Проверка

| Код | Что ловит |
|---|---|
| PT001 | форма: `## Ш7 · Название`, строки `ключ: значение`, ключи из списка, без повторов |
| PT002 | шага нет в «Истории» или внешний шаг `C-N` без контракта |
| PT003 | `приложение` не из `client · staff · admin · external` |
| PT004 | экрана нет в «Истории» |
| PT005 | контракта нет или это `service-db` — данные хранилища показываются в панели сами |
| PT006 | поля нет в «Запросе» или обязательное поле без значения |
| PT007 | поля нет в «Ответе» |
| PT008 | кода нет в «Ошибках» контракта |
| PT009 | остались места `{{…}}` |
| PT020 | предупреждение: контракт ни на одном шаге — стык не показан заказчику |
| PT021 | предупреждение: вызов без `показать` |

Несколько вызовов на шаге — один ввод и один ответ: поля проверяются по объединению контрактов шага.

## Что собирается

```
prototype/
  spec.md               план показа — источник, правится руками
  docker-compose.yml    web (8080) и api (8000)
  web/                  index.html, runtime.js, runtime.css, spec.js — без сети и внешних библиотек
  api/main.py           FastAPI одним файлом: маршрут на каждый op контракта
  api/spec.json         контракты и шаги — вход MockAPI
  README.md
```

Всё, кроме `spec.md`, собирает `./blueprint.py prototype build` — руками не правь: правь план показа,
«Историю» или контракты и собери снова.
