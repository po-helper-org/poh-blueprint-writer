## Использование

```
/system-requirements [текст | путь к файлу] [--bft <путь к БФТ>] [--project <epic>-blueprint]
```

**Параметры:**
- `[текст | путь к файлу]` — описание задачи: контракты (или решение TO-BE из ADR), системы, где какие данные лежат. Файл — тот же текст целиком.
- `--bft <путь>` — опц., БФТ эпика: функциональные и интеграционные требования — откуда брать контракты и системы.
- `--project <epic>-blueprint` — опц., проект Service Blueprint: навык допишет секцию «## Контракты» в `plan/map.md`, применит её (`./blueprint.py apply`) и заполнит остальные разделы в документе.

## Примеры

```
/system-requirements Делаем скидку по билету: контракты ticket-validation и discount-applied-event из ADR; билеты отдаёт API билетного оператора, промокоды — каталог акций
/system-requirements brief.md --bft .bft/documentation/skidka-bileta/skidka-bileta.md
/system-requirements brief.md --project skidka-bileta-blueprint
```

## Что делает

1. Читает вход: контракты — из решения TO-BE ADR, ИТ-требований БФТ и описания существующих интеграций; системы и где какие данные лежат.
2. По каждому контракту отвечает на три обязательных вопроса (три колонки таблицы «Контракты»): (1) какие данные нужны контракту; (2) откуда берётся каждый параметр — `параметр → система / сервис / поле|справочник`; (3) какие преобразования нужны для контрактов и бизнес-логики. Пустых ячеек нет: «не знаю» = `[УТОЧНИТЬ]`.
3. **Не выдумывает.** Источник или преобразование не сказаны во входе — ячейка `[УТОЧНИТЬ: …]` и вопрос в «Открытые вопросы». Про состояние источников спрашивает, если вход молчит.
4. Данных критически не хватает (нет ни контракта, ни системы) — возвращает только вопросы, документ не строит.
5. С `--project`: кладёт «## Контракты» в `plan/map.md` и прогоняет `./blueprint.py apply` (документ «Системные требования» создастся, apply переписывает только «Контракты»); заполняет «## AS-IS», «## Изменения», «## Открытые вопросы» прямо в документе; открытые вопросы дублирует в «## Вопросы» плана («Где» — ID контракта K1…); `./blueprint.py lint` — гейты AR (форма таблиц, три вопроса без пустых ячеек, имена контрактов как в «Решении TO-BE» ADR).

Формат ответа и правила — `../skills/system-requirements/SKILL.md`; эталоны — `../skills/system-requirements/examples/` (вход с пробелами и вход без данных).

## Важно

**Честность важнее полноты.** Лучше вопрос без источника, чем источник, придуманный за владельца системы. Каждое `[УТОЧНИТЬ]` имеет вопрос; каждый открытый вопрос — свою причину.

**Навык не выбирает архитектуру и не проектирует новые контракты** — это ADR: здесь только данные для уже решённых контрактов. Не выдаёт доступы и не трогает системы — это Delivery. Вопросы людям не рассылает: список «кому — что» отдаётся владельцу.
